## 1. Joplin のプラグイン全般

### 1.1 ノートビューアの CSP：WebAssembly と Web Worker は使えない

- **何が起きたか**: PlantUML の Graphviz（WASM 版）を使う図がエラーになった。Web Worker も作れなかった。
- **原因**: ノートビューアの CSP（Joplin 3.7.22）は次のとおりだった。
  - `script-src 'self' joplin-plugin://* joplin-content://*` で、`'wasm-unsafe-eval'` を含まない。そのため WASM をコンパイルできない。
  - `child-src` は YouTube などの決まったサイトだけ。Worker は、アセットの URL からも Blob URL からも作れなかった。
  - ページは `about:`、プラグインのアセットは `file:` の URL で読み込まれる。
- **対応**:
  - Graphviz（`viz-global.js`）は同梱せず、PlantUML 内蔵の Smetana レイアウトを常に使う。
  - エンジンはメインスレッドで動かす。
- **次のプラグインへの示唆**:
  - **WASM や Worker が前提のエンジンは、そのままでは Joplin のビューアで動かない。** エンジンを選ぶ前に確かめること。例えば Graphviz 系や、Rust を WASM にした描画ライブラリが当てはまる。
  - 純粋な JavaScript で動くエンジンを選ぶ。重い処理は、デバウンスとキャッシュで回数を減らす（1.6節）。
  - CSP は、試作のプラグインで `document.querySelector('meta[http-equiv="Content-Security-Policy"]')` を表示させれば確かめられる。`WebAssembly.compile` と `new Worker(...)` も、試作の中で実際に試すのが確実。

### 1.2 エンジンの読み込み：ES モジュールの動的 import は使える

- **何が起きたか**: エンジン（ES モジュール）を、ビューアから `import(URL)` で読み込めた（40〜140ms）。`eval` や `new Function` は CSP で使えない。
- **対応**: ビューアスクリプトの URL（`document.currentScript.src`）からフォルダの URL を求め、その下のエンジンを `import()` する。
- **注意（ビルド）**:
  - webpack が `import()` を自分のチャンク読み込みに変えないよう、`import(/* webpackIgnore: true */ url)` と書く。
  - TypeScript の `module` が `commonjs` だと、`import()` が `require()` に変わってしまう。ビューアのビルドだけ `module: 'es2020'` にする（1.8節）。
- **次のプラグインへの示唆**: 図のブロックがあるときだけエンジンを読み込む（遅延読み込み）。そうすれば、図のないノートへの影響はほぼゼロになる。

### 1.3 エンジンのファイルはアセットとして宣言しない

- **何が起きたか**: 設計書では、エンジンのファイルを Markdown-it プラグインのアセットとして宣言する予定だった。
- **原因**: アセットとして宣言したスクリプトは、ノートを表示するたびに `<script>` として読み込まれる。図のないノートでも、数 MB のエンジンが読み込まれてしまう。
- **対応**: 宣言するのは `viewer.js` と CSS だけにした。エンジンのファイルは `dist/contentScript/engine/` に置くだけにし、ビューアが必要なときに読み込む。プラグインのフォルダにあるファイルは `file:` の URL で読める。

### 1.4 リッチテキストエディタ：Joplin 本体のコードブロックと同じ形の HTML にする

ブロックを `<div class="joplin-editable">` と `<pre class="joplin-source">` の組み合わせで出力すると、リッチテキストエディタが Mermaid と同じように扱う。図が表示され、ダブルクリックで Joplin 標準の編集画面が開く。ただし、細部を Joplin 本体の形に合わせないと、ソースが壊れる。

| 問題 | 原因 | 対応 |
| ---- | ---- | ---- |
| 保存や編集のたびに空行が増える | `pre.joplin-source` にソースの末尾の改行を残していた。Joplin は「開きフェンス」「ソース」「閉じフェンス」をそのままつないで Markdown に戻す | Joplin 本体（`packages/renderer/MdToHtml.ts`）と同じく、ソースの末尾の改行を1つ除く。その改行は、閉じフェンスの属性 `data-joplin-source-close` の先頭（`&#10;`）に持たせる |
| 編集画面で OK を押すと、ブロックのオプション（`theme=dark` など）が消える | 編集画面は `data-joplin-language` の値を言語の欄に出し、OK でそれを info 文字列として使う | `data-joplin-language` に、言語名だけでなく info 文字列全体（例: `plantuml theme=dark`）を入れる |
| 4文字のフェンスが3文字に変わる | 編集画面は、フェンスを必ず3文字で組み立て直す（`useEditDialog.ts` の `newBlockSource`） | Joplin 本体の制約として受け入れた。Mermaid も同じ。ソースに ```` ``` ```` を含むブロックは壊れることがあると README に書く |
| 編集画面で OK を押すと、図が描かれず回転表示のままになる | OK のあと、Joplin はブロックの**外側の要素を残し、中身の HTML だけを差し替える**（`editable.innerHTML = editableInnerHtml(result.html)`）。プラグインは「描画済み」の印を外側の要素に付けていたため、新しい中身を描画済みと誤って判断した | 描画済みの印を、中身の側（図の出力の要素）に付ける。中身が差し替えられると印も消える |

- **次のプラグインへの示唆**:
  - 7.1節の HTML の形（末尾の改行を除く、`&#10;` で始まる閉じフェンス、info 文字列全体）は、どの図のプラグインでもそのまま使える。
  - **描画の状態は、Joplin に差し替えられる側の要素に持たせる。** ブロックの外側の要素はリッチテキストエディタに残されることがある。
  - 手動テストには、次の手順を必ず入れる。
    - リッチテキストエディタとの切り替え
    - 編集画面で何も変えずに OK を押す
    - 編集画面でソースを変えて OK を押す
  - 推測で直すより、Joplin 本体のソースを読む方が早かった。調べた場所は 3章にまとめた。

### 1.5 ビューアの更新の仕組み

- **`joplin-noteDidUpdate`**:
  - ノートを編集すると、入力のたびに届いた（3.7.22）。
  - 編集中はビューアは読み込み直されず、本文の HTML だけが差し替えられる。
  - リッチテキストエディタでも、Joplin がエディタの中の文書にこのイベントを送る。
- **テーマの切り替え**:
  - Joplin のテーマを切り替えると、ノートビューアが丸ごと読み込み直される。
  - そのため、ビューアスクリプトが起動時に背景色から明暗を判定するだけで、テーマに追従できた。スタイルの変化を見張る仕組みはいらない。
- **補助**: `MutationObserver` も併用し、未処理のブロックがあるときだけ処理する。同じ処理を何度呼ばれても問題ないように作る。
- **次のプラグインへの示唆**: ビューアスクリプトは複数回実行されることがある。`window` に印を付け、1ページで1回だけ初期化する。

### 1.6 編集中のちらつき対策

本文の HTML は入力のたびに丸ごと差し替えられるので、何もしないと入力のたびに図が消えて描き直される。

| 対策 | 内容 |
| ---- | ---- |
| キャッシュ | ソース、テーマ、プリアンブル、設定版数、エンジン版数からキーを作る。変更のない図は、エンジンを呼ばずにすぐ表示する |
| 直前の図を残す | 描画中は、同じ位置（ページ内で何番目のブロックか）の直前の図を半透明で表示する |
| 別のノートの図と区別する | 同じ位置でも、別のノートに切り替えたときは前の図を出してはいけない。ノートの ID はビューアからはわからないので、ソースの「先頭と末尾の共通部分」が全体の半分以上なら、編集中と判断する |
| デバウンス | 編集中と判断したブロックだけ、描画を 300ms 遅らせる。新しく開いたノートはすぐ描く |
| 直列キュー | エンジンは1件ずつ呼ぶ。描画の前に `el.isConnected` を確かめ、差し替えで消えた要素は飛ばす。同じ位置の古い要求も捨てる |
| エラーのとき | 入力の途中は構文エラーになりやすい。エラーボックスの下に直前の図を薄く残し、図の高さが上下しないようにした |

オーナーの評価では、Mermaid と比べてちらつきや入力の重さは気にならなかった。

### 1.7 テーマ：背景色の明るさで判定する

- `getComputedStyle(document.body).backgroundColor` の相対輝度で判定する。body が透明なら html を見る。判定できなければ Light とする。
- 実測した値は、Light が `rgb(255, 255, 255)`、Dark が `rgb(29, 32, 36)`。しきい値は中間の灰色（輝度 0.18）にした。
- Joplin のテーマの一覧を持たずに済み、利用者が独自の CSS で背景を変えていても合う。
- **背景の問題**:
  - **何が起きたか**: 次の組み合わせで、線や文字が背景に埋もれて読めなかった。
    - Light テーマのノートで、`theme=dark` を指定した図
    - Dark テーマのノートで、`theme=none` を指定した図
  - **原因**: エンジンは、Light でも Dark でも図の背景を塗らない。SVG に背景の要素がない。最初は「背景を透明にする指定をやめれば、エンジンが背景を塗る」と考えたが、誤りだった。
  - **対応**: 図のスタイルの明暗とページの明暗が違うときだけ、CSS で SVG の後ろに背景色（白 `#ffffff` または `#181818`）を敷く。ソースには何も足さない。ヘッドレスの Chrome と Joplin 3.7.22 の両方で、Light / Dark のどちらのテーマでも読めることを確認した。
- **次のプラグインへの示唆**:
  - 「エンジンが背景を塗るか」は、エンジンごとに確かめる。
  - 図ごとにテーマを指定できるようにするなら、ページと明暗が違うときの見え方を最初から考えておく。

### 1.8 プラグインジェネレーター（`yo joplin`）とビルド

| 問題 | 対応 |
| ---- | ---- |
| `yo joplin --silent` でも質問が出て止まる | 作業用のフォルダで `--update --silent --skip-install --force` を使って雛形を作り、`src` などをテンプレートからコピーした |
| `src` からコピーしただけの JS（エンジン）も、webpack が Terser で圧縮し直す。取得元のファイルと同じであることを確かめられなくなる | CopyPlugin の設定に `info: { minimized: true }` を付ける。`.jpl` の中のエンジンが `vendor/` と同じであることを、SHA-256 で確かめた |
| `extraScripts` は CommonJS（`target: 'node'`）でビルドされる。Markdown-it プラグインにはそれでよいが、`<script>` で読まれるビューアスクリプトでは動かない（`exports` がない） | ビューア用の webpack の設定を別ファイル（`webpack.viewer.js`）にした。`target: 'web'` の普通のスクリプトとしてビルドし、`buildExtraScripts` の段に追加した。ジェネレーターの `webpack.config.js` の変更は1行で済む |
| ビューアのビルドで `module: 'es2020'` にすると、TypeScript のモジュール解決の既定が `classic` になり、`api` や `dompurify` が見つからなくなる | ts-loader の `compilerOptions` に `moduleResolution: 'node'` も指定する |

### 1.9 SVG の安全性

- エンジンの SVG は、挿入する前に DOMPurify（SVG のプロファイル）で無害にする。
- テストでは、悪意のある SVG が無害になることと、実際の図の線や文字が1つも消えないことの両方を確かめた。
- エラーメッセージなど、エンジンから来た文字は `textContent` で入れる。`innerHTML` は使わない。

### 1.10 ネットワークを使わないことの確認

- ヘッドレスの Chrome で、テスト用の自前のファイル以外へのリクエストをすべて止め（`context.route`）、記録した。止めた件数は0件だった。
- **落とし穴**: コンソールに `net::ERR_NAME_NOT_RESOLVED` が出たが、原因はブラウザが自動で取りに行くファビコンだった。ページから出た要求ではない。テスト用のページに `<link rel="icon" href="data:,">` を入れると消える。プラグインの通信と取り違えないこと。
- **記録の方法は組み合わせる**（段階1 の手順4）。正式なテスト（`npm run test:render`）では、次の3つを組み合わせた。
  - ルートで止めて記録する（`context.route`）
  - ページの読み込みが終わったらオフラインにする（`context.setOffline(true)`）。オフラインでも、ルートで返すファイルは読み込める
  - テスト用のページに CSP を付け、違反を記録する
- **CSP の方が先に止める**: 外部のサイトへの要求は CSP がネットワークより先に止めるので、ルートの記録には出ず、CSP の違反として出る。片方だけを見ていると見落とす。
- **検査そのものを試すテストを入れる**: わざと通信を起こしても検出できることを確かめる。実際に、最初に試した `<img>` タグは記録されなかった。原因は、テスト用の Markdown-it が既定で HTML を無効にしていて、タグがただの文字になったことだった。Markdown の画像（`![x](URL)`）に変えると検出できた。
- **わざと壊して確かめる**: テストがすべて一度で通ったので、実装を一時的に壊して、テストが失敗するかを確かめた。
  - エンジンの Dark の指定を常に有効にすると、テーマのテストが失敗した（検出できた）。
  - Smetana の指定を外しても、テストは通った。Graphviz を同梱していないと、エンジンが自動で Smetana を使うためで、テストの見落としではない。

### 1.12 Git の改行コード

- `core.autocrlf=true` の Windows では、ブランチを切り替えると作業ファイルの改行が CRLF になる。
- 同梱するエンジンは `.gitattributes` で `vendor/** -text` とし、取得元とバイト単位で同じに保つ。エンジンのファイルには、取得元の時点で CRLF のものもあった。

- 唯一の手がかりは、CodeMirror 6 のエディタが 3.1 から標準になったことだった。そこで 3.1 にした（動作確認は最新の安定版だけで行う）。

### 1.14 公式プラグイン一覧の掲載条件（調査時点）

- npm パッケージ名は `joplin-plugin-` で始め、キーワードに `joplin-plugin` を入れる。

### 1.15 設定とビューアへの受け渡し（段階2）

- **設定を変えると、すぐに図に反映された**（V-10。Joplin 3.7.22）: プラグインの設定を変えてノートに戻ると、何もしなくても図が新しい設定で描き直された。Joplin がノートビューアを描き直すため。設定の変化をビューアに知らせる仕組みを、別に作る必要はなかった。
- **設定画面の文字列の入力欄は1行**（V-09）: API の設定の種類（`SettingItemType`）に複数行の入力欄はない。複数行の値（カスタムのプリアンブル）は、1行で入力して `\n`（バックスラッシュと n）で改行を表す方式にした。本物の改行も受け付けるようにしておく。
- **Markdown-it プラグインからも設定を読める**: `plugin(markdownIt, pluginOptions)` の `pluginOptions.settingValue(キー)` で、プラグインの設定を読める（API の型定義のコメントに記載）。言語名の別名のように、HTML を作る段階で必要な設定はこれで読む。失敗しても描画が止まらないよう、例外を受け止める。
- **ビューアは `webviewApi.postMessage(コンテンツスクリプトの ID, メッセージ)` でメインスクリプトに問い合わせる**: メインスクリプトは `joplin.contentScripts.onMessage(ID, ...)` で答える。ID は、Markdown-it プラグインを登録したときの ID を使う。
- **問い合わせの仕方**: 最初の表示だけは設定が届くまで待つ（既定値で描いてから描き直すと、ちらつく）。2回目以降は手元の設定ですぐに描き、裏で問い合わせて、変わっていたときだけ描き直す（キャッシュからの表示を、問い合わせの往復で遅らせない）。設定版数は、設定の値のハッシュ値にすると、数え上げる仕組みがいらない。
- **受け取った設定は検査する**: 型や範囲がおかしい値は既定値に置き換え、ビューアが壊れないようにする。問い合わせに失敗したとき（`webviewApi` がない、など）も既定値で描く。
- **テストの落とし穴**: Playwright の `addInitScript` に渡す関数は、そのままページの中で動く。TypeScript で `async` 関数を書くと、`__awaiter` などの補助関数を使う形に変換され、ページの中で見つからずに失敗した。ページに渡す関数では `async` を使わず、`Promise.resolve` で書く。

## 2. PlantUML に固有の事柄（別のエンジンを選ぶときの確認項目）

| 項目 | 判明したこと | 別のエンジンで確かめること |
| ---- | ------------ | -------------------------- |
| 公式の JS 版 | `@plantuml/core`（TeaVM で Java を JS に変換したもの）。1.2026.6 以降は MIT で、内蔵して再配布できる。CheerpJ 版は実行時に CDN からランタイムを読むので使えない | ライセンスが内蔵と再配布を許すか。実行時に外部から何かを取得しないか |
| 外部からの読み込み | 本体に通信の API はない。外部から読もうとするのは、`themes.js`、標準ライブラリ（`PLANTUML_STDLIB_LOADER`）、ローカルの `!include`（`PLANTUML_FILE_LOADER`）の3つだけで、どれも差し替えられる | エンジンが外から読み込む経路をすべて洗い出し、プラグインで止められるか |
| 標準ライブラリ | `!include <C4/...>` などの標準ライブラリは含まれない。読み込み関数を差し替えて常に失敗させ、エラーとして表示する | 図の部品の「ライブラリ」をエンジンが外から読むか |
| 絵文字・アイコン | `emoji.js`（1.9MB）と `openiconic.js` は、標準ライブラリと同じ読み込み関数を通る。この2つだけ同梱のファイルを渡し、使われたときだけ読む。絵文字の名前は `thumbsup` などで、`+1` はない | 大きな付属データを遅延読み込みにできるか |
| Graphviz | クラス図などは Graphviz（WASM）を使う。Joplin では WASM が動かないため、`!pragma layout smetana` を自動で入れて、内蔵の Smetana で描く。品質はほぼ同じ。Graphviz がなくても、エンジンは自動で Smetana を使った | レイアウトに WASM や外部のプログラムを使うか。純粋な JS の代わりの手段があるか |
| エラーの返し方 | 構文エラーは `onError` ではなく、エラーを描いた SVG として返る。SVG の `<text>` の文字から `[From textarea (line N) ]` を探して、行番号とメッセージを読み取る（画像解析ではなく文字列の処理）。クラッシュは "An error has occurred!" と "has crashed" で見分ける。エンジンの SVG をそのまま出すと、版数の欄に `$version$` が出る | エラーがどの形で返るか。行番号を取り出せるか |
| 行番号のずれ | プリアンブル（自動で入れる行）を入れると、エラーの行番号がずれる。挿入した行数を記録して補正する。`@startuml` を省略したブロックに自動で足した行も補正の対象にする | 自動で行を足すなら、行番号の補正を最初から設計する |
| プリアンブルの対象 | `skinparam` を受け付けるのは `@startuml` の図だけ。`@startjson`、`@startmindmap` などには入れない（段階1）。`theme=none` でも Smetana の指定だけは入れる（描画に必要なため） | 図の種類ごとに、スタイルの指定方法が違うか |
| Dark の見た目 | エンジンの `dark` オプションで、十分に読みやすい Dark の図になる。そのため、独自の Dark の配色（`joplin-dark`）は作らずに済んだ | エンジンに Dark のモードがあるか。あれば配色の表を作る手間が省ける |
| 背景 | Light でも Dark でも背景を塗らない（1.7節）。内蔵テーマ（`cyborg` など）でも塗らない。`skinparam backgroundColor` で色をはっきり指定したときだけ、SVG の `style` に `background-color` が付く。そのため、設定の「背景を透明にする」が効くのは、プリセットなどで背景色を指定した場合だけ。プリアンブルでは、設定画面で選んだ項目（背景、フォント、文字サイズ）をプリセットの行より後に置き、プリセットより優先させた（段階2） | 背景を塗るか。どの指定で塗るか |
| 内蔵テーマ（`!theme`） | `themes.js` に43個（空の `_none_` を除く）。各テーマの先頭に名前、表示名、説明、作者、ライセンスのヘッダーがあるが、明暗を示す情報はない。そのため、Light 用・Dark 用のどちらの選択肢にも全部出した。一覧は `themes.js` から生成し、一致をテストで確かめる。`!theme` は、プリアンブルの中でプリセットの行や設定より前に置く | テーマの一覧を機械的に取れるか |
| 図の種類ごとの見た目の指定 | 段階2 で、`@startuml` 以外の図の種類に、プリアンブルの候補を1つずつ入れて調べた。どの候補もエラーにはならなかった。`<style>` の `root { FontSize / FontName }` は、マインドマップ、WBS、ガント、JSON、YAML、EBNF、正規表現に効いた。`skinparam defaultFontSize` / `defaultFontName` は JSON、YAML、正規表現に効かない。salt と chronology には、どちらも効かない。利用者が図の中に書いた指定は、どちらの書き方のプリアンブルよりも優先された。中身が PlantUML の書き方でない種類（ditaa、dot、math など）は、行を足すと図が壊れるので、確かめた種類だけに入れる「許可リスト」にした | 図の種類ごとに、見た目の指定が効くか。足した行で図が壊れる種類がないか |
| 壊れた JSON | `@startjson` の中身が JSON として正しくなくても、エラー（`[From textarea (line N) ]`）にはならない。「Your data does not sound like JSON data」という文を図として描く | エラーとして扱われない入力がないか |
| SVG の比較 | SVG に `data-source-line`（元のソースの行番号）が入るため、プリアンブルを1行足すだけで、見た目が同じでも SVG の文字列は変わる。見た目の変化を調べるときは、文字サイズやフォントなどの属性を取り出して比べる | − |
| `<style>` の範囲 | `element { BackGroundColor ... }` のように広い範囲に塗りを指定すると、アクティビティ図の開始・終了の黒丸が白抜きになり、クラス図の「C」「I」の丸の色も消えた。図の意味が変わるので、`joplin-light` では文字と線（`root`）、シーケンス図の参加者、ノートだけを指定した | スタイルの指定が、意味を持つ色まで変えてしまわないか |
| CJK | Canvas で測らず内蔵の情報で文字幅を決めるが、日本語・中国語・韓国語ではみ出しはなかった | 日本語を含む図で、文字のはみ出しや重なりがないか |
| 速度 | 読み込み約 0.3 秒、最初の図約 0.15 秒、2回目以降は1図 5〜30ms。メインスレッドでも問題にならなかった | Worker が使えないので、メインスレッドで動かしても十分速いか |
| 文字サイズ | SVG の `font-size` から最小の文字サイズを読み取れる | 縮小表示の調整に必要な情報を SVG から取れるか |
| 描画の間に残る状態（不具合） | クラス図などを描いた後、次のシーケンス図がクラス図として描かれることがある。描画のたびに小さな図を先に描かせて対処した（2.1節） | **前の描画の結果が、次の描画に影響しないか。** 図を単独で描いた結果と、他の図に続けて描いた結果を比べるテストを、最初から入れる |
| 縦に長い図 | 縦か横が 8192px を超える図は、エンジンが「Diagram too large for browser rendering」のエラーにする（`maxSvgSize` で変えられる）。1000行のシーケンス図で起きた | 大きさの上限があるか。利用者にどう見えるか |
| とても長い1行 | 2万文字の行は、意味の読めないメッセージ（`java.lang.UnsupportedOperationException ...`）のエラーになる。固まりはしない | 異常な入力でのエラーの出方 |
| 無限ループ | `!while` の無限ループや無限の再帰は、エンジン自身が検出して行番号つきのエラーにした。固まらなかった | 異常な入力で止まらなくならないか |
| タイムアウト | メインスレッドで動くので、時間切れの表示はできても、描画そのものは止められない | 長い処理を中断できるか |
| サイズ | エンジン一式で約 5.5MB（Graphviz を除く） | パッケージサイズ。10MB を目安にした |

### 2.1 描画の間に残る状態（エンジンの不具合）

- **見つけた経緯**: 段階1 の手順5 の準備で、M-16 用のノートを試しに描いたときに見つけた。1000行のシーケンス図が、単独では「大きすぎる」のエラーになるのに、ノートの中では描画に成功し、図の大きさも違っていた。
- **起きること**: クラス図、ユースケース図、状態図、コンポーネント図のどれかを描くと、その次に描く「参加者を宣言していないシーケンス図」（メッセージが10行程度以上）が、クラス図として描かれる。参加者がクラスの箱になり、メッセージがクラス間の矢印になる。
- **確かめたこと**: プラグインのコードを通さず、エンジン単体でも起きた。`participant` で参加者を宣言すると起きない。別の種類の図（マインドマップ、アクティビティ図、参加者を宣言したシーケンス図、エラーになる図など）を1回描くと元に戻る。
- **影響**: Joplin のビューアはノートを切り替えても使い回すので、別のノートのクラス図の影響も受ける。誤った結果がキャッシュにも残る。
- **対策**: 描画のたびに、その直前に小さなシーケンス図（`participant` を1つ宣言しただけのもの）を描かせ、結果は捨てる（`engine.ts` の `RESET_LINES`）。1回あたり数ミリ秒の負担。
- **テスト**: 描画テストで、各図を単独で描いた結果と、他の図に続けて描いた結果が一致することを確かめている。この2つのテストは、対策の前のコードでは失敗し、対策の後は合格した。
- **今後**: PlantUML の開発元への報告は、当面は行わない（2026-11-19、オーナーの判断）。エンジンを更新したときは、対策なしでも直っているかを確かめる。

## 4. 進め方で役に立ったこと

- **試作（スパイク）を3段階に分けた**:
  1. コードを書かない調査
  2. ブラウザでのエンジン単体の試作
  3. 最小限のプラグイン
- **試作は使い捨てにした**: 作業用のブランチで作り、`main` にはマージせず、結果だけを設計書に反映した。
- **Joplin の中でしか確かめられないことは、試作のプラグインに診断パネルを付けて画面に出した**: CSP、WASM、Worker、イベントの回数、背景色などを表示させた。オーナーが画面キャプチャを送るだけで、結果を確かめられた。
- **Joplin に入れる前に、ヘッドレスの Chrome で確かめた**: ビルドしたプラグインのビューアスクリプトを、通信を遮断した状態で、本物のエンジンを使って動かした。実機の確認の前に大半の問題を見つけられ、実機での手戻りが減った。
- **実際のエンジンの出力をテストのデータにした**: エラーの SVG やクラッシュの SVG を保存し、単体テストに使った。
- **手動テストの入力は、渡す前にヘッドレスの Chrome で試した**: 手動テスト用のノートを作るとき、各ブロックの「期待する結果」を書く前に実際に描いてみた。そこで、単独で試した結果とノートの中の結果が違うことに気づき、エンジンの不具合（2章の「描画の間に残る状態」）が見つかった。
- **Joplin で見つかった問題は、直す前にテストにした**: 例えば「行番号が 2 から 3 にずれる」「編集画面の OK のあと描画されない」。修正前のコードで失敗することを確かめてから直した。
- **開発の道具の注意**（Claude 向け）: シェルのヒアドキュメントの中で Python や JavaScript の文字列（`\n` やバッククォート）を扱うと、エスケープが崩れることが何度もあった。ソースの書き換えは、編集用のツールで行うか、スクリプトをファイルに書いてから実行する方が確実。
